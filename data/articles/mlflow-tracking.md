MLflow Tracking — это API и веб-интерфейс. Во время работы ML-кода он записывает параметры, версии кода, метрики и выходные файлы, а потом показывает результаты. У MLflow Tracking есть API для Python, REST, R и Java.

Если вы раньше не работали с MLflow Tracking, начните с [Quickstart](https://mlflow.org/docs/latest/ml/tracking/quickstart/).

## Понятия

### Запуски (runs)

MLflow Tracking построен вокруг **запусков** (runs). Запуск — одно выполнение кода, например один вызов `python train.py`. Каждый запуск записывает:

- **метаданные** — метрики, параметры, время начала и конца и т. д.;
- **артефакты** — выходные файлы: веса модели, картинки и т. д.

### Модели

Модели — обученные ML-артефакты, которые появляются в ходе запусков. У записанной модели (Logged Model) свои метаданные и артефакты, как у запуска.

### Эксперименты

Эксперимент собирает запуски и модели одной задачи. Эксперимент можно создать из командной строки, через API или в веб-интерфейсе. API и веб-интерфейс также позволяют искать эксперименты.

## Запись запусков

API MLflow Tracking — это набор функций для записи запусков. Например, `mlflow.start_run()` начинает новый запуск. Функции записи `mlflow.log_param()` и `mlflow.log_metric()` записывают параметры и метрики.

```python
import mlflow

with mlflow.start_run():
    mlflow.log_param("lr", 0.001)
    # Ваш ML-код
    ...
    mlflow.log_metric("val_loss", val_loss)
```

Другой способ — **автологирование** (auto-logging). Оно записывает метрики, параметры и модели без явных вызовов записи. Достаточно вызвать `mlflow.autolog()` перед кодом обучения. Автологирование поддерживает популярные библиотеки: scikit-learn, XGBoost, PyTorch, Keras, Spark и другие.

```python
import mlflow

mlflow.autolog()

# Ваш код обучения...
```

По умолчанию, без настройки сервера и базы, MLflow Tracking пишет данные в локальную папку `mlruns`. Чтобы писать в другое место (удалённую базу, облачное хранилище) и делиться результатами с командой, см. раздел «Настройка окружения» ниже.

### Поиск записанных моделей из кода

В MLflow 3 есть поиск моделей: `mlflow.search_logged_models()`. Он находит модели во всех экспериментах по метрикам, параметрам и атрибутам. Синтаксис фильтра похож на SQL.

```python
import mlflow

# Найти лучшие модели в нескольких экспериментах
top_models = mlflow.search_logged_models(
    experiment_ids=["1", "2"],
    filter_string="metrics.accuracy > 0.95 AND params.model_type = 'RandomForest'",
    order_by=[{"field_name": "metrics.f1_score", "ascending": False}],
    max_results=5,
)

# Взять лучшую модель для развёртывания
best_model = mlflow.search_logged_models(
    experiment_ids=["1"],
    filter_string="metrics.accuracy > 0.9",
    max_results=1,
    order_by=[{"field_name": "metrics.accuracy", "ascending": False}],
    output_format="list",
)[0]

# Сразу загрузить лучшую модель
loaded_model = mlflow.pyfunc.load_model(f"models:/{best_model.model_id}")
```

Главное:

- **фильтр как в SQL**: префиксы `metrics.`, `params.` и атрибуты модели;
- **учёт набора данных**: метрики можно фильтровать по конкретному набору данных, чтобы честно сравнивать модели;
- **гибкая сортировка**: по нескольким критериям сразу;
- **прямая загрузка**: новый формат адреса `models:/<model_id>`.

### Поиск запусков из кода

Всё, что умеет веб-интерфейс, доступно из кода через `MlflowClient`. Например, найдём запуск с лучшей (наименьшей) ошибкой на валидации в эксперименте:

```python
client = mlflow.tracking.MlflowClient()
experiment_id = "0"
best_run = client.search_runs(experiment_id, order_by=["metrics.val_loss ASC"], max_results=1)[0]
print(best_run.info)
# <RunInfo: run_id='...', experiment_id='0', status='FINISHED', start_time=...>
print(best_run.data.metrics)
# {'val_loss': 0.123}
```

## Запись моделей

В MLflow 3 в одном запуске можно записать несколько контрольных точек (чекпоинтов) модели и следить за их качеством на разных наборах данных. Это удобно в глубоком обучении: чекпоинты с разных этапов обучения сохраняются и сравниваются.

### Чекпоинты модели

Чекпоинт на нужном шаге записывают с параметром `step`. Каждая записанная модель получает уникальный ID, по нему её потом находят.

```python
import mlflow
import mlflow.pytorch

with mlflow.start_run() as run:
    for epoch in range(100):
        # Обучение модели
        train_model(model, epoch)

        # Чекпоинт каждые 10 эпох
        if epoch % 10 == 0:
            model_info = mlflow.pytorch.log_model(
                pytorch_model=model,
                name=f"checkpoint-epoch-{epoch}",
                step=epoch,
                input_example=sample_input,
            )

            # Метрика, привязанная к этому чекпоинту
            accuracy = evaluate_model(model, validation_data)
            mlflow.log_metric(
                key="accuracy",
                value=accuracy,
                step=epoch,
                model_id=model_info.model_id,  # связь с конкретной моделью
                dataset=validation_dataset,
            )
```

### Связь метрик с моделями и данными

В MLflow 3 метрику можно привязать к конкретному чекпоинту и набору данных. Так проще проследить, откуда взялось качество модели:

```python
# Ссылка на набор данных
train_dataset = mlflow.data.from_pandas(train_df, name="training_data")

# Метрика со связью с моделью и набором данных
mlflow.log_metric(
    key="f1_score",
    value=0.95,
    step=epoch,
    model_id=model_info.model_id,  # связь с чекпоинтом
    dataset=train_dataset,  # связь с набором данных
)
```

### Поиск и ранжирование чекпоинтов

`mlflow.search_logged_models()` находит и сортирует чекпоинты по метрикам:

```python
# Все модели запуска, по убыванию accuracy
ranked_models = mlflow.search_logged_models(
    filter_string=f"source_run_id='{run.info.run_id}'",
    order_by=[{"field_name": "metrics.accuracy", "ascending": False}],
    output_format="list",
)

# Лучшая модель
best_model = ranked_models[0]
print(f"Best model: {best_model.name}")
print(f"Accuracy: {best_model.metrics[0].value}")

# Загрузить лучшую модель для предсказаний
loaded_model = mlflow.pyfunc.load_model(f"models:/{best_model.model_id}")
```

### Адреса моделей в MLflow 3

В MLflow 3 новый формат адреса модели: по ID модели, а не по ID запуска.

```python
# Новый формат MLflow 3
model_uri = f"models:/{model_info.model_id}"
loaded_model = mlflow.pyfunc.load_model(model_uri)

# Заменяет старый формат через запуск:
# model_uri = f"runs:/{run_id}/model_path"
```

Плюсы:

- **прямая ссылка**: не нужно знать ID запуска и путь к артефакту;
- **жизненный цикл модели**: у каждого чекпоинта свой ID;
- **сравнение**: легко сравнить чекпоинты одного запуска;
- **прослеживаемость**: ясные связи между моделями, метриками и данными.

## Запись наборов данных

MLflow умеет записывать наборы данных, связанные с обучением. Их метаданные сохраняет функция `mlflow.log_input()`. Подробнее — в [документации MLflow по данным](https://mlflow.org/docs/latest/ml/dataset/).

## Просмотр запусков, моделей и результатов

### Веб-интерфейс Tracking UI

Tracking UI показывает эксперименты, запуски и модели. Он умеет:

- показывать запуски по экспериментам и сравнивать их (в том числе из разных экспериментов);
- искать запуски по значению параметра или метрики;
- рисовать графики метрик;
- скачивать результаты запусков (артефакты и метаданные).

То же доступно и для моделей.

Если запуски пишутся в локальную папку `mlruns`, выполните в папке над ней команду и откройте в браузере [http://127.0.0.1:5000](http://127.0.0.1:5000):

```console
mlflow server --port 5000
```

Тот же интерфейс даёт сервер MLflow Tracking Server. Он ещё и хранит артефакты удалённо. Тогда интерфейс доступен по адресу `http://<IP сервера>:5000` с любой машины, которая видит сервер.

## Настройка окружения MLflow Tracking

Если вы пишете данные и модели только в локальные файлы, этот раздел можно пропустить.

MLflow Tracking подходит для разных сценариев работы. В общем виде окружение состоит из компонентов ниже.

### Компоненты

**API MLflow Tracking.** Вы вызываете их в ML-коде, чтобы записывать запуски и, если нужно, общаться с сервером MLflow Tracking Server.

**Хранилище метаданных (backend store).** Хранит метаданные каждого запуска: ID, время начала и конца, параметры, метрики и т. д. Бывает двух видов:

- на файловой системе (локальные файлы);
- в базе данных (например, PostgreSQL).

С управляемым сервисом (Databricks, Azure Machine Learning) вы работаете с внешним хранилищем через REST, к нему нет прямого доступа.

**Хранилище артефактов (artifact store).** Хранит артефакты запусков, обычно большие: веса моделей (например, сериализованную модель scikit-learn), картинки (PNG), файлы моделей и данных (например, Parquet). По умолчанию это локальная папка `mlruns`. Поддерживаются и другие хранилища, например Amazon S3 и Azure Blob Storage.

На модель, записанную как артефакт MLflow, ссылаются адресом `models:/<model_id>`, где `model_id` — уникальный ID модели. Он заменяет старый формат `runs:/<run_id>/<artifact_path>`.

Если модель зарегистрирована в MLflow Model Registry, на неё можно ссылаться и так: `models:/<имя-модели>/<версия>`.

**Сервер MLflow Tracking Server (не обязателен).** Отдельный HTTP-сервер с REST API для доступа к хранилищам метаданных и артефактов. Он позволяет настроить, какие данные отдавать, доступ, версии и т. д.

## Другие настройки Tracking Server

**Локальный сервер.** Tracking Server можно запустить у себя. По сравнению с файлами или базой это даёт немного. Но так удобно проверить командный процесс локально или запускать ML-код в контейнере.

**Режим только артефактов.** Опция `--artifacts-only` заставляет сервер обрабатывать только артефакты, без метаданных. Это полезно в большой организации или при обучении очень больших моделей: трафик артефактов огромный, и его лучше отделить, чтобы он не мешал записи метрик.

**Прямой доступ к артефактам.** По умолчанию сервер проксирует и артефакты, и метаданные. Иногда нужен прямой доступ к удалённому хранилищу артефактов, без затрат на прокси. Для этого запустите сервер с опцией `--no-serve-artifacts`.

## Частые вопросы

**Можно ли запускать несколько запусков параллельно?** Да, MLflow поддерживает параллельные запуски, например в нескольких процессах или потоках.

**Как упорядочить много запусков?**

- Сгруппируйте запуски в эксперименты — это логические контейнеры для запусков.
- Создавайте дочерние запуски внутри одного родительского. Например, по дочернему запуску на каждый фолд кросс-валидации.
- Добавляйте запускам теги. По тегам запуски можно фильтровать и искать.

**Можно ли писать в удалённое хранилище без Tracking Server?** Да. Для командной работы лучше использовать Tracking Server как прокси для артефактов, но для личных проектов и тестов он не обязателен:

1. Настройте доступ к хранилищу артефактов (ключи, адреса), как для Tracking Server.
2. Создайте эксперимент с явным местом хранения артефактов:

```python
experiment_name = "your_experiment_name"
mlflow.create_experiment(experiment_name, artifact_location="s3://your-bucket")
mlflow.set_experiment(experiment_name)
```

Запуски этого эксперимента будут писать артефакты прямо в удалённое хранилище.

**Как подключить Model Registry?** Нужно хранилище метаданных в **базе данных** (например, PostgreSQL), а модели нужно записывать методами `log_model` соответствующего вида модели. После записи модель можно добавлять, менять и удалять в Model Registry через интерфейс или API.

**Как добавить к запуску описание?** Используйте системный тег `mlflow.note.content`. Остальные системные теги ставятся автоматически, а этот — **нет**: его задаёте вы. Текст появится на странице запуска в разделе Notes.
